# PROJECT: QR LIBRARY SYSTEM
## Build a Complete, Functional Library Management Web Application

Act as a senior full-stack developer, UI/UX designer, database architect, and security engineer.

Do not just create a frontend design or static prototype. Build a functional application with a real database, authentication, QR generation, QR scanning, book registration, student management, book issuing, book returns, and inventory tracking.

# 1. PROJECT OBJECTIVE

The goal is to digitize school library operations and reduce manual register work.

The librarian should be able to:

- Register books.
- Register multiple physical copies of the same book.
- Generate ONE shared QR code for each book title/edition.
- Attach the same QR code to all physical copies of that book.
- Scan the QR code to identify the book.
- Issue a book to a student.
- Return a book.
- Track available and issued copies.
- View borrowing history.
- Search for books and students.
- View library statistics.

This application is initially designed for one school library and one librarian account.

# 2. IMPORTANT BUSINESS LOGIC: SHARED QR CODE

This is the most important feature of the application.

DO NOT generate separate QR codes for individual physical copies.

Each registered book title/edition must have:

- One book database record.
- One unique book ID.
- One unique QR token.
- One QR code shared by every physical copy.
- One total copy count.

Example:

Book: Physics, Class XI
Author: NCERT
Total Copies: 10
QR Codes Generated: 1

All 10 physical copies must use the same QR code.

The application must display:

Total Copies: 10
Available Copies: 7
Issued Copies: 3

Calculation:

Available Copies = Total Copies - Active Issued Records

Issued Copies = Number of active borrowing records for that book.

Never store the available copies as an independently editable number. Calculate availability from the database to prevent incorrect inventory counts.

When a librarian increases the total number of copies from 10 to 15, the existing QR code must remain unchanged.

When a librarian scans the shared QR code, the application must identify the book title and show its current inventory information.

IMPORTANT LIMITATION:
The shared QR code identifies a book title, not an individual physical copy. Therefore, when returning a book, the librarian must select the correct active borrowing record. Do not pretend that the system can identify which physical copy was returned.

# 8. QR CODE MANAGEMENT

Create a QR code containing a stable URL or identifier that resolves to the registered book.

Example:

/scan/UNIQUE_BOOK_TOKEN

Requirements:

- One QR token per book record.
- The QR token must remain unchanged when book details or copy counts are edited.
- All physical copies of the same book use the same QR code.
- QR code should not contain student personal information.
- QR code should be downloadable as PNG.
- QR label should include book title and a clear instruction: "Same QR for all copies".
- Support printing QR labels.

After scanning:

1. Validate the QR token.
2. Find the corresponding book.
3. Display book information.
4. Display total, available, and issued copies.
5. Display Issue Book and Return Book actions.
6. Display active borrowing records.

If the QR is invalid, display a clear error message.

Provide manual token entry if camera scanning is unavailable.

# 9. ISSUE BOOK FUNCTIONALITY

Create a functional Issue Book workflow.

Process:

1. Scan the book QR code or search for a book.
2. Open the book detail screen.
3. Display its availability.
4. Search for a registered student.
5. Select the student.
6. Enter the due date.
7. Confirm the transaction.
8. Save the borrowing record.
9. Update the dashboard statistics.

Example:

Physics, Class XI

Total Copies: 10
Available Copies: 7
Issued Copies: 3

A librarian issues one copy to Ravi Kumar.

New inventory:

Total Copies: 10
Available Copies: 6
Issued Copies: 4

Business rules:

- A book cannot be issued when no copies are available.
- Do not allow negative availability.
- Every successful issue must create an issue record.
- Record issue date and due date.
- Record which student borrowed the book.
- Prevent accidental duplicate submissions.
- Ensure that simultaneous issue requests cannot exceed available stock.

Use a Firestore transaction or trusted server-side operation for inventory-changing operations. Ensure concurrent issue requests cannot exceed available stock.

- Prevent returning the same record twice.
- Store the actual return date.
- Calculate availability from active borrowing records.
- Keep historical issue records permanently unless an authorized retention policy is introduced.

# 13. FIRESTORE DATA DESIGN

Use Cloud Firestore collections and documents rather than SQL tables or migrations.

Use these collections:

COLLECTION: books

- Document ID: book ID
- title, author, subject, class_grade, publisher, isbn
- total_copies (positive integer)
- qr_token (unique token)
- is_archived
- created_at, updated_at

COLLECTION: students

- Document ID: student ID
- admission_number (unique)
- full_name, class_name, section
- created_at, updated_at

COLLECTION: issue_records

- Document ID: issue record ID
- book_id (book document ID)
- student_id (student document ID)
- issue_date, due_date
- return_date (null while active)
- created_at

Do not store a separate available_copies field. Calculate it as total_copies minus active issue records.

Use Firestore Security Rules to restrict reads and writes to authorized librarians. Validate inventory-changing operations so concurrent issue requests cannot exceed available stock.

Do not store a separate available_copies field.

Do not create a separate physical-copies table in this MVP.
